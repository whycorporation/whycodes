# Phase 4 — CI quality budgets

**Status:** not started · **Depends on:** nothing · **Blocks:** nothing

Cheapest phase here and independent of the others. It can run alongside any of
them.

## Problem

CI enforces formatting, clippy and tests. That catches a lot, but it does not
catch slow drift: a `unwrap()` added under pressure, an error quietly discarded
with `let _ =`, a dependency pulled into a crate that should not have it, a
binary that grows 40% over a month.

jcode gates all of these with scripts that fail the build when a counted budget
is exceeded:

```
check_panic_budget.py            check_swallowed_error_budget.py
check_warning_budget.sh          check_dependency_boundaries.py
check_code_size_budget.py        check_test_size_budget.py
check_wildcard_reexport_budget.py
```

The budgets live in JSON next to the scripts (`panic_budget.json`,
`swallowed_error_budget.json`, …), so lowering one is a visible commit.

This directly concerns work already done in this repo. On 2026-07-30 we found
that `cmd_stats` swallows a database error with `Err(_) => { … return Ok(()) }`
while `cmd_session` propagates it — and that asymmetry is exactly why the
macOS failure took three CI rounds to diagnose. A swallowed-error budget would
have made it visible.

## Goal

Counted quality properties are ratcheted: they can improve without ceremony and
can only worsen deliberately.

## Scope

In:

- Panic budget: count `unwrap()`, `expect()`, `panic!()`, `todo!()`,
  `unimplemented!()` in non-test code.
- Swallowed-error budget: count `let _ =` on a `Result`, `Err(_) =>` arms that
  discard, and `.ok()` used to drop an error.
- Binary size budget for the release build.
- Dependency boundaries: assert the crate graph, e.g. `core` must not depend
  on `tui`.
- A ratchet rule: a budget may be lowered in any commit; raising one requires
  editing the JSON, which shows up in review.

Out:

- Warning budget. `-D warnings` already means zero, so a budget adds nothing.
- Startup and memory budgets. Those need Phase 5's harness first.
- Test-size and wildcard-reexport budgets. Fine ideas, low value at 24k lines.

- [ ] `scripts/check_dependency_boundaries.py` reading an allowed-edges list
- [ ] A `budgets` job in `ci.yml` running all of them
- [ ] `docs/budgets.md`: what each budget means, how to lower one, and what
      justifies raising one
- [ ] Triage the initial swallowed-error count and fix the ones that hide real
      failures — starting with `cmd_stats`

## Acceptance criteria

- [ ] Every budget script runs on Linux, macOS and Windows, or is explicitly
      restricted to one and the CI job says so
- [ ] Adding an `unwrap()` to non-test code fails CI
- [ ] Removing one and not updating the JSON still passes — the ratchet is
      one-directional
- [ ] Raising a budget without editing its JSON is impossible
- [ ] Each script prints the offending file and line, not just a count
- [ ] `core` depending on `tui` fails the boundary check
- [ ] The initial commit does not raise any budget to accommodate existing code
      it could instead fix

## Risks

- **Budgets become noise.** If the first run seeds a number nobody intends to
  lower, this is bureaucracy. Pair the seeding commit with an actual reduction
  so the ratchet starts moving.
- **Python in CI.** It adds a runtime dependency to the pipeline. Acceptable —
  GitHub runners have Python — but the scripts should not need packages.
- **Counting is crude.** `unwrap()` in a test helper is fine; in a request path
  it is not. Exclude `#[cfg(test)]` and `tests/` and accept the remaining
  imprecision.
